# Python 并发：线程、进程、协程怎么选

一句话先记住：**多线程/协程省的是"等"，多进程要的是"算"，而能不能提速，取决于和你打交道的那一方到底在干什么。**

## 一、先看两个反直觉的例子

**多线程读本地硬盘上的多个文件，能加速吗？**

不能。瓶颈在磁盘，单块盘的顺序读就那么多带宽，线程再多也只是排队。反而每次 2ms 量级的线程切换会额外吃掉 CPU。

**多线程读文件的同时还要写远程数据库，能加速吗？**

能写之前先等数据库的网络往返，这段等待期 CPU 是闲着的，多个连接可以并行，直到打满数据库的写入上限。

结论：**同一份"IO 代码"，加速与否取决于对端的工作方式和承载能力**，而不是"它是不是 IO"。

## 二、任务怎么分

- **IO 密集型** —— 读写文件、stdin/stdout/stderr、打印、上传下载、查服务器、查数据库、拍照/录像。瓶颈在等待外部设备或网络返回。
- **CPU 密集型** —— 算分形点、估算 π、素数因式分解、解析 HTML/JSON、文本处理、跑模拟。瓶颈在 CPU 指令周期。

现实里大多数任务并不纯粹：一个爬虫既等网络又解析 HTML，一个数据处理脚本既读盘又算。判断方法是**看时间花在哪**：`cProfile` 里大块时间停在 `read`、`recv`、`execute`，就是 IO；停在计算函数上，就是 CPU。

## 三、三种并发手段各解决什么

| 手段 | 解决的问题 | 适用 | 代价 |
|---|---|---|---|
| 多线程 | IO 等待时，让进程的 CPU、内存去干别的活 | IO 密集型，等待占比高 | GIL 下同一时刻只有一个线程跑 Python 字节码；线程多了切换有开销 |
| 多进程 | 真要并行计算，绕开 GIL，吃满多核 | CPU 密集型 | 进程启动、内存复制、进程间通信（序列化）成本高 |
| 协程 | 用单线程承载成千上万个"等待中"的任务 | 高并发 IO（网络服务、批量请求） | 全链路要 async，混入同步阻塞调用会卡住整个事件循环 |

选择顺序可以粗暴成这样：**等外部 → 协程/线程；吃满 CPU → 进程；两者都有 → 拆开，IO 段用异步、计算段丢进程池。**

## 四、协程的几个容易踩的点

- 底层是操作系统的事件通知：Linux 上的 epoll（另有 select / poll），配合 `yield` 让出控制权；Python 3.4 起由 `asyncio` 统一调度。
- `await` 只能出现在 `async def` 里。
- `async` 只是把函数注册成"可被事件循环调度的协程"，**没有 `await` 的 async 函数，宏观上和同步代码没区别**——它一次跑到底，中途不会让出。
- 一旦在协程里调了同步阻塞的东西（`time.sleep`、同步 `requests`、同步数据库驱动），整个事件循环停住，所有并发一起卡死。
