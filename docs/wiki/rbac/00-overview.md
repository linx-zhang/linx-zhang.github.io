
# RBAC 设计解析：一套多租户平台的权限底座

这是对一个 41 MB、24 张表的 `mysqldump` 导出做的全量解析：一套多租户物联网平台的权限底座 + 低代码后台引擎，MySQL 8.0.24，业务数据截止 2021-12。所有数字都来自逐行拆解 dump（建表语句 + 15.9 万行 INSERT），不是抽样估算。

它值得读的地方，是把「权限」拆成了三层各自独立表达：功能到操作、数据行到一段 SQL、列到掩码；也是把「表怎么变成页面」这件事本身数据化了。优点和风险同源——都来自「把 SQL 当配置」。

## 一、这套系统是什么

16 个业务模块（物联卡、物联设备、支付、智能电梯、资产管理、智慧工地、消防…），527 个逻辑模型、6,499 个字段元数据，全靠配置驱动页面；权限侧以「组织」为租户域，用三层权限 + 一段 SQL 片段解决数据隔离。

## 二、七个核心结论

1. **规模不大，但结构完整**：24 张表；权限相关 10 张（资源/功能点/行策略/列掩码/角色/4 张关联/组织可见），元数据 7 张，主体 3 张，其余 4 张为审计/凭证/流水号。

2. **权限分三层，各自独立表达**
   - 功能：`_resource`(1,192) → `_acl_func`(3,704) → `_role_acl_func`(16,789)，粒度到「操作」；
   - 行：`_acl_data`(397) 存 **WHERE 片段 + JOIN 片段**，用 `$user.orgId` 模板变量；
   - 列：`_role_prop`(33)，只有 33 条且 mask 全为 0。

3. **最巧的一招：拆出「数据过滤角色」**
   58 个角色里有一批只授功能、一批只授数据。58 个角色 / 483 条用户角色边 / 170 个多角色用户，其中 **162 个用户同时持有「业务角色 + 数据过滤角色」**。功能与数据视野解耦、可叠加复用。

4. **最险的一招：行权限就是一段 SQL**
   397 条策略覆盖 366 个模型，其中 329 条只有 `join`、62 条带 `cond`、5 条用 `EXISTS`。核心句式只有一个：
   `JOIN _org ON … JOIN _org_owner ON … AND _org_owner.ownerOrgId = $user.orgId`
   一段可复制的文本养活了 300+ 张表，也把安全边界放在了字符串上。

5. **组织闭包表替代树遍历**
   `_org`(217，181 个根) + `_org_owner`(659 条边，132 个组织有多个上级，组织 1 管 84 个) —— 一次 JOIN 解决「上级能否看下级」，还支持非树形的代理授权。

6. **元数据把「表」和「页面」都数据化了**
   `_model`(527) / `_prop`(6,499) / `_model_table`(472) / `_model_relation`(113) / `_dict`(855)。8 个模型直接用整段 SQL，0 个用存储过程；`uiData.mask` 与 `_acl_func.funcKey` 共用词表，前端渲染与后端鉴权不脱节。

7. **配置漂移是最大的治理问题**
   `_menu` 219 份 JSON 中 107 份的 `orgId` 已不在 `_org`；`_sysconfig` 327 份里 86 份是孤儿；同一菜单节点在 310 份 JSON 里各存一份；`_org` 有 4 个悬空 `parentId`。**原因是这些关联全都没有外键**。

## 五、一条判断

它的强项是「用极低成本覆盖极多表」，弱项是「把 Safety 依赖放在了自由文本和人工配置上」。若要复用，保留「组织闭包 + 双轨角色 + 资源/功能点」的骨架，把行权限从 SQL 片段换成结构化谓词，就能同时拿到灵活性和可维护性。
