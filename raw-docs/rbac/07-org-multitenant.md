# 组织与多租户：组织树、管理归属与白标

整套系统的「租户」就是**组织**。没有 `tenant_id`，没有分库，所有业务表共用 `org_id`/`orgId` 列，再加两张关系表（`_org_owner`、`_role_owner`）控制「谁能管谁」、「角色在哪生效」。

---

## 一、组织树 `_org`（217 条）

| 字段 | 含义 |
|---|---|
| `id` | 主键 |
| `parentId` | 上级组织（`NULL` = 根） |
| `name` | 组织名（`UNIQUE org_name`） |
| `code` | 组织编码（`UNIQUE org_code`） |
| `desc` | 描述 |
| `domain` | 独立域名（部分组织有自己的域名） |
| `defaultPage` | 登录后默认落地页（如 `dashboard`、`/device/device`） |

### 1.1 形状：浅树 + 大量平铺租户

```text
总 217 条
根组织（parentId 为空）181 个   ← 83% 是平铺的独立租户
有子节点的组织        26 个
parentId 悬空（指向不存在的组织）4 个（573/574/575/674）
```

这不是一棵「集团 → 分公司 → 部门」的典型深树，而是**大量独立租户 + 少量代理/子公司挂在下面**的结构。这与业务模式一致：平台方（组织 1 智能物联）卖 SaaS 给不同客户，每个客户一个根组织；代理商的租户再通过 `_org_owner` 挂到代理名下。

典型组织：

```text
1  智能物联（super）         默认页 dashboard   ← 平台方自己
4  全芯微（uc）
6  XX公司（xx）
13 物联卡测试（card-test）
14 云支付音箱（speaker）      默认页 /device/device
34 共享设备应用（device-share）
```

`defaultPage` 的存在说明**白标不仅是颜色/logo，连「这个租户进后台先看到哪一页」都是按租户配的**。

---

## 二、管理关系 `_org_owner`（659 条）—— 真正的多租户控制面

| 字段 | 含义 |
|---|---|
| `orgId` | 被管理的组织 |
| `ownerOrgId` | 管理方组织 |

```sql
PRIMARY KEY (ownerOrgId, orgId)
KEY roleId (orgId)         -- 命名误写为 roleId，实际索引的是 orgId
```

**这是一张「谁管谁」的图，不是树**：

```text
659 条边 · 274 个不同管理方 · 217 个组织
一个组织被多个上级管理：132 个（多代理/多上级交叉管理）
一个上级管理多个组织：组织 1 → 84 个；组织 524 → 74 个；组织 79 → 40；571 → 33；574 → 31
```

它解决了 RBAC 里最麻烦的一件事：**「上级组织的人能不能看到下级组织的数据」**。答案不是靠树形递归，而是靠这张关系表直接 JOIN —— 所以 `_acl_data` 里那句 `JOIN _org_owner ON _org_owner.orgId = _org.id AND _org_owner.ownerOrgId = $user.orgId` 才能一次命中全部下级。

**为什么用关系表而不是树遍历？**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 递归查 `parentId` | 语义自然 | 每次查询要递归/物化路径，MySQL 8 早期版本没有 CTE 递归优化，性能差 |
| **关系表 `_org_owner`（本方案）** | 一条 JOIN 搞定；支持多上级、跨层级、非树形授权（A 能管 C，但 C 不挂在 A 下面） | 关系要人工/程序维护；组织增删要同步维护边；无深度/路径字段 |

事实上的表现也证明了这一点：**组织 1 管 84 个组织，而 `_org` 里根组织有 181 个** —— 说明关系表里有相当多是「非父子」的授权（跨租户代理），这是树结构能力之外的东西。

## 三、角色可见组织 `_role_owner`（1,713 条）

| 字段 | 含义 |
|---|---|
| `roleId` | 角色 |
| `orgId` | 该角色可用的组织 |

```sql
PRIMARY KEY (roleId, orgId)
```

语义：**一个角色只在列出的组织内生效**。这解决了「角色定义是全局的，但授权是局部」的问题 —— 同一个「物联卡管理员」角色，可以只在组织 1、3、7 生效，而不影响其他租户。

实测规模：

```text
1,713 条边 · 45 个角色 · 108 个组织
角色可见组织最多：配置管理员 86、物联卡管理员 85、物联卡短信管理员 85、
                微信H5支付申请 85、物联卡组织管理员 85
部分角色 0 条：账户管理员、设备管理员、支付管理员、短信管理员、
              数据过滤系列（31/42/43/44/53）  ← 这类角色是"功能/数据策略包"，本身不绑组织
```

**这印证了 03 里的双轨角色设计**：

- 「功能角色 / 数据过滤角色」不绑组织（`_role_owner` 为空），它们只是一组权限包；
- 真正「在哪些组织生效」由**业务角色**绑定的 `_role_owner` 决定；
- 数据行的实际范围再由 `_acl_data` 里的 `$user.orgId` + `_org_owner` 收敛。

三层叠加后的有效范围 = `角色可见组织` ∩ `用户组织可管理范围` ∩ `行策略过滤`。

⚠️ 但这种「三重收敛」没有显式优先级：如果某角色在组织 A 生效，而用户属于组织 B（B 不管 A），结果取决于 SQL 拼接形状，而不是一条可读的规则。这是 09 里会点出的设计债之一。

## 四、菜单：每个组织一份 JSON `_menu`（219 条）

| 字段 | 含义 |
|---|---|
| `id` | 主键 |
| `json` | 整棵菜单树（JSON 文本） |
| `updateDate` | 更新时间 |
| `orgId` | 所属组织 |

**不是「菜单表 + 角色菜单表」，而是「一个组织一份菜单文档」**。JSON 结构就是前端路由树：

```json
[
  { "path": "/dashboard", "component": "/dashboard/index",
    "meta": { "title": "监控中心", "icon": "dashboard" } },
  { "path": "/system", "meta": { "title": "系统配置", "icon": "setting" },
    "redirect": "/system/model",
    "children": [
      { "path": "/system/model", "meta": { "title": "领域模型" }, "key": "/system/model", "title": "领域模型", "parent": "/system" },
      { "path": "/system/prop",  "meta": { "title": "模型属性" } },
      { "path": "/system/dict",  "meta": { "title": "字典管理" } },
      { "path": "/system/org",   "meta": { "title": "组织管理" } }
    ] },
  { "path": "/auth", "meta": { "title": "账户与权限", "icon": "user" },
    "redirect": "/auth/user",
    "children": [ { "path": "/auth/user" }, { "path": "/auth/role" }, { "path": "/auth/resource" } ] }
]
```

字段里同时存在 `meta.title` 和顶层 `title`、`key`、`parent` —— **新旧两版前端约定的痕迹并存**，属于历史兼容字段。

### 4.1 真相：菜单是可复制的配置，不是可治理的数据

```text
219 份菜单 · 195 个不同 orgId · 但只有 88 个 orgId 还能在 _org 里找到
→ 107 份菜单的 orgId 已不存在（组织被删/改名/测试残留）
常见菜单节点（跨组织复制次数）：
  /card/wl_channel 310 · /card/config/index 310 · /card/order/wl_renew_order 310
  /card/wl_rebate_set 310 · /card/stock/card 306 · /push 293 · /card/cmpp/smsSending 280
  /auth 219 · /auth/user 219 · /auth/role 219 · /system 217 · /system/org 217
```

**同一个节点在 310 份菜单 JSON 里各存了一份**。要改一个菜单标题（比如「物联卡」改名「物联网卡」），就改了 310 处。这是这套设计里**最明显的「配置漂移」风险**：

- 无法回答「哪些租户有这个菜单」（要解析 219 份 JSON）；
- 无法做菜单级灰度/回收（只能改 JSON 文本）；
- 组织删除后菜单残留（107 份孤儿）。

### 4.2 菜单与权限的衔接

JSON 只决定「**菜单里有哪些节点**」，节点是否可见还要过 `_resource(type='menu') → _acl_func(viewEnabled)`（详见 04）。二者是**「菜单结构 × 权限裁剪」** 的双层结构：

```text
菜单 JSON（这个租户的菜单长什么样）
   ∩ 用户角色拥有的 viewEnabled（这个用户能看哪些）
   = 实际渲染出来的菜单
```

这个双层设计是对的（结构归租户、可见性归用户），问题只在 JSON 副本的治理上。

## 五、白标配置 `_sysconfig`（327 条）

| 字段 | 含义 |
|---|---|
| `id` | 主键 |
| `json` | 配置 JSON |
| `updateDate` | 更新时间 |
| `orgId` | 所属组织 |

键集合（327 条全部包含前三个键）：

```json
{
  "logo": "智能物联网平台",          // 平台名（注意：键叫 logo，存的是文字标题）
  "desc": "数据管理与分析，自动化构建平台",
  "copyright": "Smart Supertom 2019",
  "beian": "…",                      // 备案号（315 条）
  "logoChart": "…",                  // logo 图（288 条）
  "shortLogo": "…"                   // 282+
}
```

```text
327 条 · 303 个不同 orgId · 但 _org 只有 217 个 → 86 条孤儿
```

和 `_menu` 同样的问题：**每个租户一份完整 JSON 副本，无模板继承、无版本、组织删了配置留着**。

## 六、账号与组织的关系 `_user.orgId`（39,819 条）

```text
orgId 分布 TOP：14 → 36,593（92%）· NULL → 2,907 · 1 → 62 · 34 → 7 · 510 → 6 · 13 → 5
isActive：1 → 39,811，0 → 8
```

**组织 14（云支付音箱）一个人装了 3.66 万个账号**，占全库 92%。这说明 `_user` 不只是「后台员工账号表」，而是**同时承载 C 端/设备侧账号池**（支付音箱的商户/终端用户）。潜在问题：

- 后台员工账号与外部账号混用同一张表、同一套权限体系；
- 按 `username` 唯一约束（`ix_user_username`），意味着这 3.6 万个账号的名字空间与内部员工共享，容易冲突；
- 38,819 个账号只产出 483 条 `_user_role` 边 —— 绝大多数 C 端账号**根本没有角色**（它们走另一套认证路径，如 `login_by_mobile`）。

日志可以佐证：`_log` 里 80,789 条 `login`，其中 70,113 条是 `https://iot-we.com/api/user/login_by_mobile` —— **绝大多数登录来自移动端/微信侧账号，而不是后台**。所以「权限系统」实际只服务于少数后台账号（约 170 个多角色用户 + 88 个单角色用户）。

## 七、多租户设计的整体评价

### 做对的地方

1. **组织即租户，`org_id` 普及到几乎所有业务表** —— 让「一条 JOIN 管到底」成为可能；
2. **`_org_owner` 关系表替代树遍历** —— 支持多上级、跨层级、非树形代理授权，性能好（一次 JOIN）；
3. **`_role_owner` 把「角色定义」与「角色生效范围」分开** —— 同一角色可复用到多个租户；
4. **`defaultPage` + `_sysconfig` + `_menu` 三件套** —— 白标到「进哪个页面、叫什么名字、什么 copyright」都能按租户配；
5. **C 端账号与后台账号同表**，简化了「一个手机号既是员工又是终端用户」的场景（代价见上）。

### 需要修的地方

| 问题 | 证据 | 建议 |
|---|---|---|
| 配置副本无治理 | `_menu` 107 份孤儿、`_sysconfig` 86 份孤儿 | 改为「模板 + 差异覆盖」，或至少加 `orgId` 外键 + 删除时清理 |
| 组织树残缺 | 181 个根组织、4 个悬空 `parentId` | 补全层级或明确「平铺即租户」的语义；补 `depth/path` 便于统计 |
| 关系表无深度字段 | `_org_owner` 只有边 | 加 `depth`、`path`，或至少加「是否包含下级」的语义列 |
| 三重收敛无优先级 | `_role_owner` / `_org_owner` / `_acl_data` 各管一段 | 明确「以哪一层为准」，最好把组织范围收敛成一条后端统一谓词 |
| 用户池混装 | org 14 占 92% 账号 | 拆 `_user`（后台）与 `_member`（C 端），或加 `userType` 区分 |

## 八、小结

组织这一层是整套方案的「地基」：**权限最终都落在「组织」这个维度上收敛**。作者的取舍非常工程化 —— 宁可用一张关系表 + 一段 SQL 片段，也不引入复杂的策略引擎。代价是「关系表需要人工维护、副本 JSON 会漂移、多重收敛缺乏优先级」，这三条构成了 09 里 P1 级问题的主体。
